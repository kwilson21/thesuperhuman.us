6 · Behind the paths

One brief and one pipeline (option A), unchanged

Naming the paths makes the earlier recommendation stronger: one more path costs a few labels, while a new request kind per path would cost a production table rebuild each time.

A · Paths in one brief

Recommended
BriefOfferAgreementStripe invoiceProject page
  • About 20 files, no database migration. Every path stays kind software.
  • 14 two-path checks in four files (path === 'idea' ? … : 'workflow') become lookups.
  • The brief page adapts to the path: dot count, link field and single-choice screens.
  • /services rows come from a list instead of two fixed rows.

Drift: low.

B · A request kind per path

Not recommended
BriefOfferAgreementStripe invoiceProject page
  • owner_requests.kind has a CHECK constraint: each new kind is a table-rebuild migration on production D1.
  • 16 files branch on kind, including SQL in offers, invoices, signing and project pages.

Drift: high, and it grows with each new path.

Misses the goal
BriefOfferAgreementStripe invoice
  • Website leads still end as an email with no way to an offer, agreement or invoice.

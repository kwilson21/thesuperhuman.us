The request reaches the library untouched, so repeated and empty parameters are treated as on `origin/main`. The library's operations on the namespace were listed from its source (version 1.2.3): `get` of `client:<client id>` (the id comes from a parameter, a Basic header or the unverified issuer of a client assertion), `grant:<user>:<grant>` (the first two parts of a code, a refresh token or an access token) and `token:<user>:<grant>:<hash>` (the first two parts of a token, the hash is fixed length), of `transaction:<hash>` (a hash) and of the client-assertion replay marker (`get` and `put` of a fixed prefix plus the SHA-256 hex digest of the visitor-sent issuer and jti, a fixed length, so the claim that no visitor can drive a `put` over the limit still holds); `put` and `delete` only of keys it generated itself (a registered client's id is 16 generated characters; a grant and its tokens are keyed by the signed-in owner's id and generated ids; a transaction by a hash) or read back from a record it stored; `list` only by the prefix of a grant it has already found by a `get`; `getWithMetadata` is not used. The wrapper therefore answers an over-long `get` and `getWithMetadata` as not found, an over-long `list` prefix as empty, does nothing for an over-long `delete`, and lets any `put` through (an over-long `put` cannot be driven by a visitor, so if it ever failed it would be a store failure, as it would be).

## Where the protocol wins over the standing rules (a judgment call, for the owner to confirm)

- MCP tools answer in the protocol's shape: HTTP 200 with a JSON-RPC result whose text holds `{status: ...}`. An unexpected failure is `unavailable` (read) or `pending` (delivery, retry the same envelope), as `docs/publication-agent-protocol.md` tells the agent. The 500 rule does not apply to a tool result; the HTTP answer is always 200. Unchanged on A and B.
- The OAuth library's own answers (`invalid_grant`, `invalid_client`, `invalid_request` and the rest, with their statuses and JSON) are produced by `@cloudflare/workers-oauth-provider` and pass through untouched. The site's code never turns one into another status.
- The work feed's `409 {"status":"conflict"}` (stale revision, event id reused, an entry that is not what the operation needs), `410 {"status":"withdrawn"}` and `400 {"status":"rejected"}` are the receiver's documented answers and are unchanged. After three guarded tries that all find the revision taken, the answer is the same 409 conflict.
- The probe has no fixed sentence, so a transport failure answers a bare 500 as it did when it threw; adding a sentence would be new copy.

## OAuth and bearer tokens

- The work feed's bearer token: compared as SHA-256 digests, every byte read (no early exit), the token and the header never logged or echoed; a header over 4096 characters, a missing or empty configured token and any other scheme are all `401 {"error":"Unauthorized."}`. The decision is `src/server/rules/publication-token.ts`; the hashing is the flow's.
- Authorization codes, access and refresh tokens, their hashes, expiry and one-time use live inside `@cloudflare/workers-oauth-provider` over `OAUTH_KV`; the site's code neither issues, stores nor compares them. Read in the library (version 1.2.3): a code is consumed by clearing the wrapped key in its grant record, and a second use revokes the grant (`invalid_grant`, "Authorization code already used"); a refresh rotates the token and keeps the previous one for one retry. KV has no compare-and-set. An independent review's assessment, confirmed in the library: the grant is read, checked and saved with a plain put, so a second exchange of the same code can succeed for up to about a minute (KV's propagation), and it requires the code, the PKCE verifier and the client credentials, so the loss is the reuse-revocation protection, not new access. Unchanged from main; not changed here. UNVERIFIED: the timing (not observed). The library's default `onError` logs request descriptions without secrets, also unchanged from main. Nothing in this area logs or echoes a code, token or secret: the sign-in handler's failures carry no text, and a defect is logged only through `logUnexpected`.
- The login cookie (AES-GCM under `PUBLICATION_COOKIE_KEY`) carries one sign-in's state; it is single-purpose, expires after ten minutes, is marked approved once, and a consent page cookie cannot approve twice. No change of who may call what.

## Changes on B that a reader should know (all shown neutral)

- The journal commit was one batch whose INSERT decided every outcome in its WHERE (revision, event id, entry state, operation). It is now: admit (an expected revision of the largest safe integer is rejected before anything is read); one batch that reads the project's latest revision, the event under the event id and the operations of the entry; the rule (`commitPublication`); one batch that inserts the row, erases the entry's content for a withdrawal, and reads the receipt back (the database stamps `published_at`). The table's constraints are the guard: the primary key on project and event id, and `UNIQUE (project_id, revision)`. Every accepted write takes the next revision (`expectedRevision + 1`, and the rule only writes when `expectedRevision` is the latest), so two writers that read the same latest revision aim at the same revision and one is refused; that index is the compare-and-set for every fact the rule read, a withdrawal and a repeated event id included. The loser reads again and decides again, three tries in all (`decideAndSave`), so a writer that lost to the same event answers duplicate and one that lost to a different event answers conflict or withdrawn. A retried withdrawal is not "nothing to do": it writes the erasure again, which changes no stored value, because the old journal did and the corpus's digests of touched tables record it.
- The feed's current entry and history were chosen by subqueries and a JOIN. They are now pure rules over plain reads (`publication-feed.ts`): the index read (one batch) takes the latest revision and the small columns of every event of the project (revision, entry id, operation, origin, publish time, and whether its text was erased: no text); `daysToRead` names the publish events of the entries that are not withdrawn; the day read (one batch, statements of at most 50 revisions) takes each one's day (`json_extract(payload,'$.occurredOn')`, a projection of one stored field, not a decision); `chooseFeed` picks the current entry and the history (newest day first, the later publish first on a tie, backfill history only), the first 100 and ten spare; then the text of the picked events only is read by project and revision, in statements of at most 50 revisions (D1 allows 100 bound values), and `showFeed` reads each story and builds the answer from the first 100 that still have text. The bound: a request reads the small columns of every event of the project (a few hundred bytes each, no text), one projected day for each entry that may be shown, and at most 110 texts, plus the current entry's, whatever the journal holds. The earlier estimate of about 6 KB of text per event was wrong: the limits count UTF-16 units (a headline of 140, a summary of 1,000 and a technical detail of 4,000 are 5,140 units), and a unit can take up to 3 bytes in UTF-8, so an event's stored text can reach about 16 KB with its keys. A withdrawal that lands between the reads erases a picked text; the rules treat an entry whose text is gone as withdrawn and leave it out, and the next spare entry takes its place, so the history has the 100 entries a request just after the withdrawal would show (an independent review's finding; a flow test drives that interleaving with 101 entries and compares the answer with a fresh read). Up to ten entries withdrawn in that window are covered; more would leave the history shorter until the next request. Any shown story that does not read as a publication still makes the whole feed refuse, and a spare that is not shown is never read as one. A stored text that is not valid JSON on an entry that may be shown fails the day read (`json_extract` raises), a store failure that answers the same 500 and the same MCP `unavailable` as `StoredPublicationInvalid` and as the fixes branch; a stored text of a withdrawn entry is never parsed, as on A. Tested: the feed route for a shown entry with corrupt text (500, fixed sentence) and for corrupt text left on a withdrawn entry (200, nothing shown), both on A and B; the progress tool on B for a shown entry with corrupt text (`unavailable`, `isError` true). The tool's answer for corrupt text on a withdrawn entry is not tested separately; it reads the same feed. The latest revision is read as `MAX(revision)`, null for a project with no event, and the rules default it to 0; the corpus's failure patterns were changed to match the statement text and the answers did not change. Those three `on:` pattern edits in the corpus test files were made in the same commit as the store change, not in an earlier commit; the history is not rewritten.
- `src/lib/publication/oauth.ts` moved to `src/server/publication-oauth.ts` (it needs the flows, and `src/lib` may not import `src/server`); both route files re-export it from there. `src/lib/publication/mcp.ts` stays where CLAUDE.md names it and takes the tools as an argument. `src/lib/publication/oauth-login.ts` keeps only the consent page, its stylesheet and the constants (its own test checks the page against `global.css`). `src/lib/publication/journal.ts` and `website.ts` are gone: `websiteFeed` is `src/server/publication-feed.ts` and the five building pages import it from there.
- One small shared reader of a request body to a limit, `src/server/bounded-body.ts`, serves the work feed and the OAuth route (the two had the same loop).

## Model

`verification/publication-journal.qnt` (module `publication`, six properties, seven mutants, and one scripted run; `docs/verification.md`, "The publication-journal model"). The code's two reads are one step and its insert is one step with the two unique constraints as the guard; the mutant `SplitRead` reads them apart and breaks `retryNeverConflicts`; `NoRetry` breaks the same property; `NoRevisionKey`, `AnyRevision`, `NoWithdrawnRule`, `NoNewEntryRule` and `NoTargetRule` break the other five. A ghost flag is set from the real outcome and names no mutant. An independent review found that the first version of property 6 was false on the unchanged model (it compared a delivery's answer with the journal when the delivery judged, not when it read, so a correct conflict for a stale read was counted as wrong; random simulation missed it). The ghost now counts a conflict only when the same envelope was stored when the delivery made its last read, or when its insert last met a constraint; the trace is a scripted run (`staleReadTest`, run by `tests/scripts/publication-journal-trace.test.ts` with `quint test`), which fails on the old ghost and passes on the new. `NoRetry` (the insert meets the constraint, the delivery stops, the same envelope is stored) and `SplitRead` (the event id is read, another delivery stores the envelope, then the latest revision is read) still break the property; the other five properties are invariants over the stored events and have no read-time ghost. An ad hoc run of 300,000 samples of 25 steps finds no violation of the real design. The OAuth authorization code exchange is a read then a write inside the library; it is not modelled here (the library's code, KV).
